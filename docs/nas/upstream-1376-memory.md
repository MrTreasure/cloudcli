# CloudCLI v1.37.6：升级、图片与缓存修复

日期：2026-10-27。源码从官方 v1.37.5 正常 merge 到 v1.37.6。本报告前半记录源码验收阶段；后续用户已明确授权发布，前端验证通过，后端切换最终状态以维护指南所列独立任务 `result.json` 为准。

## 根因与修复范围

1. 官方 v1.37.6 未修改 `session-history-cache.service.ts` 和 Codex 主历史读取器。旧缓存按原始 JSONL 文件字节估算预算，并允许最新一个条目突破预算；没有闲置到期，在途加载也能在 invalidate 后回填。
2. 这条约 1 GiB 原生历史的前次冻结盘点显示，约 83% 字节与图片 data URL 有关，大量来自工具结果和 47 次 `compacted.replacement_history` 的重复图片。Codex 原生上下文压缩会写入快照，不等于缩小磁盘历史；WebP 网络优化也不会追溯修改旧 rollout。
3. GUI 原本只显示压缩边界、工具文本，却先将所有快照和工具图片 JSON 完整分配后再丢弃。新流式投影在缓冲/解析之前跳过这些 GUI 不使用的字节；原始文件不变，模型请求、加密推理、fork 原生边界不变。已知原生字段顺序采用快速路径，未知格式保留普通解析；不对任意提示词做正则删除。
4. GUI 可见用户内嵌图片可无损存为 `~/.cloudcli/assets/history-<sha256>.<ext>`，同图共用路径，沿用已有鉴权读取。写盘失败保留内嵌预览。新图片资产是预览引用，需随 assets 一起备份；本次未删除历史或旧图片。
5. 图片上下文详情对未变化文件复用扫描结果、合并同一文件的并发扫描、每次扫描按哈希去重；缓存只保留最多 32 个文件身份，不常驻原图/Base64。源文件变化仍需重新扫描，首次检查兼容仅出现在旧压缩快照中的图片；未宣称实现增量历史索引。
6. 历史缓存按规范化结果估计内存成本，总上限 **128 MiB / 8 个会话**、5 分钟闲置到期，超限仍返回结果但不常驻；源文件身份包含路径、大小、mtime、ctime、设备/inode。失效与新加载阻止旧加载回填。预算为保守对象成本估计，不是 V8 精确堆测量，也不是整个进程 RSS 上限。

## 同一真实历史的隔离对比

使用同一份 **1,112,644,460 字节**冻结历史（同卷 reflink），旧版为升级前 `2dd64b5e`，新版为本次源码。每次独立 Node 进程和临时 HOME/数据库，不调用模型。报告只记录计数、哈希与内存指标，不记录提示词、图片内容或凭据。临时历史副本、预览图片及基准 worktree 在验证后清理。

| 指标 | 升级前 | 修复后 |
| --- | ---: | ---: |
| 首次完整读取 | 14.05 秒 | 3.81 秒 |
| 缓存命中 | 0.72 ms | 0.40 ms |
| 消息数 | 8,983 | 8,983 |
| 规范化 JSON 字节 | 43,883,358 | 43,883,358 |
| GC 后进程 JS 堆 | 80.8 MiB | 81.3 MiB |
| 本轮读取峰值 RSS | 622.9 MiB | 634.8 MiB |

本轮读取耗时下降 **72.9%**，所有消息去除临时 ID 后的语义摘要相同：`0284cd484a7c47ef68df594145ce0fb409e22baae340a40cafeff17a92d1ca7a`。该样本的可见消息没有内嵌图片，主要改善来自跳过未展示的原生快照/工具图片；不能把图片预览外置功能的理论节省计入本轮数据。

首次基准也观察到旧版约 25.96 秒、新版约 4 秒，说明 NAS 负载和 GC 存在波动。RSS 峰值没有稳定下降，GC 后实际保留堆也基本相同；不能声称内存峰值已显著改善。本次解决常驻缓存无严格上限和重复大分配路径，未给单次解析设置进程硬内存隔离。此样本新缓存估计成本约 79.6 MiB，按 128 MiB 总预算保留；没有使用单条目例外。
