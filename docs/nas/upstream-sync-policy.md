## 每次升级流程

1. **备份和检查**：检查所有未提交工作，记录当前版本/提交；保留升级前 Git 标签、数据库备份和前端入口。源码回退与数据库回退分别记录。
2. **比对官方变化**：阅读旧基线到新 tag 的发布说明/提交，标注与保留项重叠的修改，不靠整文件覆盖解决冲突。
3. **逐项验收**：对上表逐项标记“官方已覆盖、仍需保留、需要适配”。官方实现与保留行为完全等价且无功能冲突时，可以迁移实现并移除重复补丁。涉及保留项与官方功能冲突、能力删减或交互取舍时，先列出方案并等待用户确认；不能自动按官方优先裁决。明确保留的外观、TypeScript 7 和交互偏好持续保留。
4. **验证**：运行相关测试、全量前端和后端测试、类型检查、前后端构建、lint；仪表盘变更另测插件。用本机已安装 CLI 的实际协议核验 Fast/Todo/steer，记录模拟测试、真实联调和跳过项的边界。不检测公网首页，不逐个检查全部 CDN 文件。
5. **整理记录与同步源码**：所有门槛通过并审查后更新 `docs/nas/upstream-base.txt`；维护本指南及 `docs/nas/README.md` 的路径/来源/回退依赖，暂存完整源码，由 hook 生成记录。整理提交并推送主维护分支，其他电脑在干净工作区快进拉取，使用 `pnpm install --frozen-lockfile` 和各自本机配置。
6. **发布与生效**：明确报告“源码已合并、构建已通过、实例是否已生效”。收到部署指令后，NAS 使用发布器增量更新前端，仅在后端有变化时重启后端，插件按需发布；Mac 使用自己的本机流程。运行中的长任务应纳入重启影响说明。
7. **失败回退**：未发布的失败升级留在临时分支；已发布时先回退部署产物，必要时通过新的回退提交恢复主分支。数据库只有在迁移回退确有需要、停写且评估过新增数据后才恢复备份，不能因代码回退自动覆盖最新数据。
